# Fusion Music — архитектура и техническое направление

> Статус: проектирование, версия 0.1  
> Репозиторий: `21VADIMKA21/midle`  
> Цель документа: зафиксировать границы системы и решения до начала реализации.

## 1. Цель продукта

Fusion Music — веб-сервис для музыкальных заявок Twitch-сообщества. Зрители отправляют заявки, видят очередь и текущий трек; стример и уполномоченные модераторы управляют воспроизведением. Сервисная часть должна оставаться доступной независимо от того, идёт ли эфир.

Ключевое разделение:

- **Облачная часть**: сайт, авторизация, очередь, права пользователей, настройки канала, история событий.
- **Локальный проигрыватель стримера**: получает подтверждённую очередь и воспроизводит разрешённый контент на компьютере стримера.
- **OBS**: получает аудио локального проигрывателя как отдельный источник, чтобы можно было независимо управлять звуком эфира и VOD.

Облачный сайт может работать 24/7. Воспроизведение через локальный компьютер возможно только пока компьютер и проигрыватель включены и подключены к сети. Это разные требования и разные компоненты.

## 2. Критическое ограничение: права на музыку

Нельзя считать, что наличие ссылки на YouTube, Spotify или другого стримингового сервиса даёт право воспроизводить трек в эфире. Подписка на музыкальный сервис обычно предоставляет личное прослушивание, а не право публичной трансляции.

Twitch требует иметь необходимые права или разрешение на музыку. В правилах Twitch отдельно описаны ограничения для музыкальных трансляций и аудио-request-сервисов. В частности, Twitch DJ Program не является обходным решением для автоматической очереди: его правила запрещают воспроизводить запросы аудитории сразу после отправки; программа предназначена для живого DJ-выступления, а не автоматического jukebox. Участие также ограничивает создание VOD с музыкой из DJ-каталога.

### Принятое направление

1. Не реализовывать автоматическое скачивание или извлечение аудио из YouTube/Spotify.
2. Не считать произвольную пользовательскую ссылку разрешённым источником звука.
3. Воспроизведение разрешать только для источника, чьи условия явно покрывают именно наш сценарий: пользовательские заявки, автоматическое последовательное воспроизведение, Twitch live stream, монетизированный канал при необходимости и географию использования.
4. До получения такого подтверждения музыкальный провайдер остаётся блокирующим вопросом. Интерфейс, очередь и Twitch-интеграцию можно разрабатывать независимо.
5. Архитектура должна поддерживать сменные адаптеры музыкальных источников, чтобы не привязывать весь продукт к одному поставщику.

Кандидаты для дополнительной проверки, но не утверждённые источники:
- Pretzel — лицензированная библиотека для стримеров; необходимо получить письменное подтверждение допустимости внешнего request-плеера и автоматического воспроизведения заявок.
- StreamBeats — лицензия разрешает использование музыки в Twitch-контенте, но запрещает превращать канал в музыкальную радиостанцию; необходимо уточнить, допускается ли пользовательская очередь в обычном игровом/разговорном эфире.
- Музыка, права на которую принадлежат самому стримеру или предоставлены правообладателем напрямую, при условии документально подтверждённых прав на запись и композицию.

**Запрещённое допущение:** пометка «copyright-free», «DMCA-safe» или разрешение на фоновую музыку автоматически не означает разрешение на работу публичного сервиса музыкальных заявок.

## 3. Предлагаемая архитектура

### 3.1 Веб-приложение

На базе текущего Next.js-приложения:

- публичная страница канала: текущий трек, очередь, форма заявки, статус проигрывателя;
- авторизация через Twitch;
- панель стримера: управление очередью, блокировки, настройки;
- панель модератора: skip, удаление/отклонение заявок, управление голосованием;
- API для сайта, локального проигрывателя и Twitch-бота.

Текущая страница в репозитории — демонстрационный интерфейс с тестовыми данными. Она не подключена к серверу и не воспроизводит музыку.

### 3.2 Сервер и хранение

Предварительная рекомендация: PostgreSQL как основная база данных. Сервер является единственным источником истины для очереди и прав доступа.

Основные сущности:

- `users` — Twitch user ID, login, display name, аватар и дата последней авторизации;
- `channels` — Twitch broadcaster ID и настройки Fusion Music;
- `channel_roles` — внутренние роли и привязка к Twitch-ролям;
- `tracks` — метаданные трека и идентификатор в разрешённом музыкальном источнике;
- `requests` — заявка, автор, статус, время создания, причина отказа;
- `queue_state` — текущая позиция/состояние воспроизведения и версия очереди;
- `votes` — голос пользователя за пропуск текущего трека;
- `player_sessions` — состояние локального проигрывателя, heartbeat и версия клиента;
- `audit_log` — история административных действий.

Очередь не должна храниться только в браузере или локальном проигрывателе. После перезапуска сайта/сервера она должна восстанавливаться из БД.

### 3.3 Обновление в реальном времени

Для публичной очереди используется короткий серверный cache и периодическое обновление страницы. Локальный проигрыватель использует durable HTTP polling команд примерно раз в 2 секунды и heartbeat примерно раз в 15 секунд. Команды и подтверждения хранятся в PostgreSQL; потерянная команда может быть доставлена повторно.

### 3.4 Локальный проигрыватель

Устанавливаемая PWA на Chrome/Edge в отдельном окне Windows, подключающаяся к серверу по HTTPS. Её задачи:

- авторизовать конкретный экземпляр проигрывателя;
- получать следующую разрешённую композицию;
- воспроизводить её только через утверждённый адаптер источника;
- отправлять heartbeat, текущий трек и состояние воспроизведения;
- принимать команды play/pause/skip/volume;
- корректно восстанавливаться после потери сети.

Для первого релиза выбран PWA с File System Access API и IndexedDB. Окно должно оставаться открытым во время воспроизведения; перед командами требуется явное разрешение браузерного аудио. Если на целевом ПК браузерный audio engine окажется нестабильным, резервный вариант — Electron без изменения серверного протокола.

### 3.5 OBS и аудио

Локальный проигрыватель должен выводить звук в отдельное аудиоустройство/виртуальный канал, который можно добавить в OBS как отдельный источник.

Целевой сценарий настройки OBS:
- дорожка эфира: микрофон + игровой/системный звук + музыка;
- дорожка VOD: микрофон + игровой/системный звук, без музыки.

Это проектная цель, а не подтверждённая гарантия. Нужно проверить конфигурацию на реальном OBS и убедиться, что музыка действительно отсутствует в VOD и локальной записи, если это требуется. Разделение аудиодорожек не заменяет лицензию на музыку в прямом эфире.

## 4. Twitch-интеграция

### Авторизация

Использовать два OAuth flow: owner flow создаёт/подключает основной канал и запрашивает `moderator:read:chatters` и `moderation:read`; viewer flow только идентифицирует зрителя и привязывает его сессию к уже настроенному каналу. Первый владелец подключает канал через панель управления. Зритель не может создать себе канал или права владельца. Секреты и refresh tokens хранятся только на сервере; owner token зашифрован AES-256-GCM и обновляется через refresh token.

### Чат и события

Для проверки live-чата, viewer eligibility и ролей используются официальные Twitch Helix API. Синхронизация модераторов реализована через Get Moderators; EventSub/chat bot для команд в чате остаётся следующим этапом.

Команды первого этапа:
- `!трек <ссылка или запрос>` — создать заявку, если источник и права позволяют её обработать;
- `!скип` — голос за пропуск или административный пропуск в зависимости от роли.

### Роли

- **Владелец/стример** — полный доступ к настройкам, очереди, блокировкам и управлению проигрывателем.
- **Модератор Twitch** — после синхронизации официального списка модераторов может принудительно пропускать треки.
- **Зритель** — отправка заявок и один голос за пропуск текущего трека.
- Дополнительные внутренние роли (например, VIP) можно добавить после базовой модели; они не должны подменять проверку прав Twitch.

Права проверяются сервером по Twitch user ID и актуальным данным/событиям Twitch, а не по имени пользователя, присланному клиентом.

## 5. Правила очереди и пропуска

### Заявки

- Одна заявка проходит серверную валидацию до попадания в очередь.
- Лимиты частоты заявок и числа активных заявок на пользователя настраиваются.
- Повторные заявки на один и тот же трек обнаруживаются и обрабатываются по настройке канала.
- Статусы: `pending`, `queued`, `playing`, `played`, `rejected`, `cancelled`, `failed`.
- Причина отклонения фиксируется, чтобы пользователь понимал результат.

### Голосование за пропуск

Реализованная базовая логика:
- один действующий голос на Twitch user ID для текущего трека;
- повторный голос того же пользователя не увеличивает счётчик;
- голосование привязано к ID текущего трека и сбрасывается при смене трека;
- знаменатель — число пользователей, подключённых к чату канала по Twitch Helix Get Chatters; голосовать могут только пользователи, присутствующие в этом списке;
- список чаттеров кэшируется на 10 секунд; Twitch предупреждает о задержке обновления списка при входе/выходе пользователей;
- если канал не в эфире, чаттеры не проверяются, нужный OAuth scope отсутствует или API недоступен, автоматический пропуск не срабатывает; стример/модератор всё ещё может пропустить трек вручную;
- владелец и модераторы могут пропустить трек независимо от голосования.

**Зафиксированное правило:** 50% от текущего числа подключённых чаттеров, а не от общего viewer_count и не от числа уже проголосовавших. Это делает знаменатель проверяемым и одновременно ограничивает голосование пользователями, присутствующими в чате. Для этого OAuth запрашивает scope `moderator:read:chatters`; токен владельца обновляется сервером автоматически. Twitch отмечает, что список чаттеров обновляется с небольшой задержкой.

## 6. Безопасность и надёжность

- HTTPS для сайта и API.
- Проверка Twitch OAuth state и серверная валидация токенов.
- Секреты в переменных окружения/защищённом хранилище; `.env` не коммитить.
- Rate limiting для заявок, голосов и команд.
- Валидация ссылок и идентификаторов источника; запрет произвольных URL для проигрывателя.
- Защита от повторного использования запросов/команд и дублирующих событий.
- Серверная проверка ролей и владельца канала.
- Журналирование административных действий.
- Резервные копии базы и проверка восстановления.
- Локальный проигрыватель получает короткоживущую сессию/токен с ограниченными полномочиями; он не должен иметь доступ к Twitch client secret.

## 7. Предварительная технологическая схема

- Веб: существующий Next.js + React + TypeScript.
- API: сначала можно использовать серверные маршруты Next.js, если нагрузка и границы приложения остаются простыми.
- База данных: PostgreSQL.
- Доступ к БД: ORM/типизированный слой выбирается после проверки актуальной версии стека.
- Реальное время: WebSocket или SSE после проверки потребностей двусторонней связи.
- Локальный проигрыватель Windows: отдельный клиент; технология выбирается после проверки требований музыкального SDK и аудиомаршрутизации.
- Развёртывание: облачный хостинг для сайта/API/БД; компьютер стримера — для локального звука и OBS.

Текущий стек обновлён до Next.js 16.4.5, React 19.3.0 и Node.js 22 LTS. Версии фиксируются через package-lock.json; CI выполняет чистую установку через npm ci, ESLint, миграции PostgreSQL и production build. Обновления фреймворка следует проводить только через тот же полный цикл проверок.

### Дополнительные результаты проверки музыкальных интеграций (04.11.2026)

- У Pretzel ранее существовало Twitch-расширение Song Requests, но оно снято с публикации; команда указывает, что старое расширение больше не функционировало после обновления каталога. Это не подтверждает наличие доступного публичного API для стороннего request-сервиса.
- Справка Pretzel предупреждает, что скрипты, обращающиеся к частным API и превышающие лимиты, могут привести к блокировке. Не использовать reverse engineering или приватные endpoints.
- Pretzel отдельно подтверждает наличие лицензирования для вещания музыки на Twitch. Но из доступных публичных материалов не следует однозначно, что эта лицензия распространяется на внешнюю автоматическую систему пользовательских заявок.
- SoundScout (новое название/развитие Monstercat Gold) имеет Creator-tier, где Twitch указан среди разрешённых каналов. Однако в опубликованных условиях программные приложения перечислены среди сценариев, выходящих за рамки стандартных тарифов. Поэтому его нельзя считать разрешением на интеграцию с нашим приложением без письменного уточнения.
- StreamBeats разрешает синхронизацию треков с видео на Twitch, но прямо запрещает использование в качестве музыкальной радиостанции. Request-сценарий не следует автоматически приравнивать к обычному фоновому использованию.

### Уточнение по политике Twitch: аудио-заявки и риск санкций (04.11.2026)

В актуальной странице Twitch Music Reporting Process для каналов вне DJ Program отдельно назван сценарий трансляций с recorded music через **audio request playback services**. Для участвующих в этой программе правообладателей Twitch указывает возможность выдачи music reporting penalty; повторные нарушения могут привести к более серьёзным мерам вплоть до постоянной блокировки. Это не означает, что всякая лицензированная заявка автоматически запрещена: страница описывает использование музыки без соответствующего разрешения. Но она подтверждает, что request-playback — особо чувствительный сценарий, который нельзя считать обычным фоновым использованием музыки.

Поэтому до включения автоматического воспроизведения необходимо подтвердить оба уровня прав:
1. Лицензия конкретного музыкального каталога должна разрешать Twitch broadcast и именно внешний автоматический request playback.
2. Необходимо получить разъяснение/подтверждение применимости сценария от Twitch, поскольку их Music Reporting Process отдельно выделяет audio request playback services.

StreamBeats разрешает синхронизацию своей музыки с Twitch-видео, но запрещает превращать канал в music-only radio station. Это не является прямым разрешением на отдельный request-player. Pretzel подтверждает лицензирование каталога для монетизированных Twitch-трансляций, но публичная документация не подтверждает разрешение внешнему сервису управлять автоматической очередью. Ни один из этих источников не считается утверждённым для Fusion Music request playback до письменного уточнения.

Источник:
- [Twitch Music Reporting Process](https://legal.twitch.com/legal/dmca-guidelines/music-reporting-process)
- [Twitch Music Guidelines](https://legal.twitch.com/en/legal/music/20233107/)
- [StreamBeats License](https://www.streambeats.com/licensing/)
- [Pretzel licensing agreement FAQ](https://help.pretzel.rocks/en-us/articles/15281321-do-i-have-to-sign-a-contract-to-be-on-pretzel)

**Проектное решение:** сервер, очередь, Twitch-вход и интерфейс можно продолжать разрабатывать; музыкальный playback должен оставаться выключенным feature flag до письменного подтверждения.


### Реализовано после архитектурного черновика (04.11.2026)

- Публичный `GET /api/queue` читает текущее состояние из PostgreSQL, не использует демо-данные и отдаёт статус локального проигрывателя.
- Страница Fusion Music обновляет состояние очереди с сервера и явно показывает пустую очередь/отключённый плеер вместо фиктивного трека.
- `POST /api/queue/vote` принимает один голос авторизованного Twitch-пользователя за пропуск текущего трека; повторные голоса не увеличивают счётчик.
- База ограничивает канал одним треком со статусом `playing` через частичный уникальный индекс.
- В CI запускается PostgreSQL 16, применяются все миграции дважды (проверка повторного запуска), затем собирается Next.js приложение.
- Twitch OAuth привязан к `TWITCH_BROADCASTER_ID`; обычный пользователь не может создать собственный канал и назначить себя владельцем. Постоянные OAuth-токены сохраняются только для владельца.

Ограничения текущей реализации:
- Голосование пока только собирает и показывает голоса; автоматический порог пропуска не включён до подключения достоверного источника списка/количества eligible chatters.
- Физическое переключение треков не работает до появления разрешённого музыкального источника и локального проигрывателя.
- Приём новых заявок намеренно выключен, пока источник не будет подтверждён.

### Защищённый локальный каталог как резервный музыкальный источник

Если ни один внешний провайдер не подтвердит право на автоматическое воспроизведение зрительских заявок, предусмотрен резервный режим без внешнего музыкального API:

- Стример помещает в локальную папку проигрывателя только аудиофайлы, на трансляцию которых у него есть необходимые права.
- Локальный агент сканирует каталог и синхронизирует на сервер только метаданные, длительность и хеш файла; сами аудиофайлы остаются на компьютере стримера и не загружаются на сайт.
- Зрители выбирают треки из утверждённого каталога, а сервер ставит выбранный идентификатор в очередь.
- Локальный агент находит файл по хешу/идентификатору и воспроизводит его через отдельное аудиоустройство для OBS.
- Произвольные ссылки и файлы зрителей не воспроизводятся. Добавление файла в каталог — ответственность владельца канала и не заменяет проверку лицензии на публичную трансляцию.

Это позволит получить работающий request-player даже без интеграции с каталогом третьей стороны, но библиотеку придётся наполнить музыкой с подтверждёнными правами.

### Производительность публичной очереди

Публичный endpoint очереди использует короткий серверный cache на 1 секунду, чтобы не выполнять несколько запросов к PostgreSQL для каждого одновременного зрителя. После голоса за пропуск cache инвалидируется. Для одной инсталляции это снижает нагрузку без дополнительного Redis; при масштабировании на несколько экземпляров потребуется общий cache/Redis либо другой механизм инвалидации.


## 11. Подтверждение прав на локальную музыкальную библиотеку

Fusion Player синхронизирует только метаданные и SHA-256-хэши файлов; аудиофайлы остаются на компьютере стримера. Это техническое решение не подтверждает наличие прав на публичную трансляцию.

Перед открытием зрительских заявок владелец канала должен подтвердить, что имеет права или разрешение на трансляцию каждого трека текущей библиотеки в прямом эфире Twitch. Подтверждение фиксируется в `channel_settings` вместе с Twitch user ID владельца и временем.

При каждой повторной синхронизации библиотеки:
- приём заявок автоматически закрывается;
- подтверждение прав сбрасывается;
- владелец должен проверить изменившийся каталог и подтвердить права заново.

Это не юридическая проверка лицензий и не гарантия соблюдения авторских прав. Это обязательное подтверждение ответственности владельца; каталог должен содержать только музыку, на которую действительно получены необходимые права.


## 12. Twitch chat worker

Команды чата обрабатываются отдельным Node.js-процессом, который запускается вместе с веб-приложением через `npm start`. Он подключается к Twitch EventSub по WebSocket как installed chatbot с пользовательским токеном владельца канала.

Требуемые OAuth scopes:
- `user:read:chat` — чтение сообщений канала;
- `user:write:chat` — ответы от имени владельца канала;
- `moderator:read:chatters` — получение числа активных участников чата для порога голосования;
- `moderation:read` — синхронизация списка модераторов.

Команды:
- `!трек <название>` / `!track <название>` — поиск по текущей локальной библиотеке; добавляется только однозначное совпадение;
- `!скип` / `!skip` — голос за пропуск; владелец и синхронизированные модераторы пропускают трек принудительно.

Защита:
- повторные EventSub-уведомления отсекаются по message ID;
- для каждого пользователя действует короткий cooldown команд;
- голоса уникальны для пользователя и текущего трека;
- права и лимиты проверяются сервером;
- один экземпляр worker выбирается PostgreSQL advisory lock, чтобы несколько web-инстансов не запускали дублирующихся ботов;
- статус worker записывается в `service_heartbeats` и отображается в `/api/health`.

В локальной разработке worker запускается отдельно командой `npm run chat:worker`; production `npm start` запускает веб-сервис и worker под общим supervisor.


### Надёжность очереди и Twitch worker

- Перед каждой выдачей команды `play` сервер проверяет, что приём заявок включён и подтверждение прав на текущую библиотеку не сброшено.
- Синхронизация новой библиотеки закрывает приём заявок до повторного подтверждения. Уже поставленные в очередь треки сохраняются, но не запускаются; после повторного подтверждения очередь продолжает работу.
- Событие `started` проверяется сервером до фактического запуска аудио в браузере-проигрывателе.
- Все операции, которые одновременно меняют настройки канала, очередь и устройство проигрывателя, используют согласованный порядок блокировок PostgreSQL.
- Twitch refresh token обновляется под блокировкой строки в БД; worker и сервер используют один механизм сериализации, чтобы не перезаписывать друг другу ротируемые refresh tokens.
- Перед использованием worker проверяет токен через Twitch OAuth Validate и сверяет Twitch user ID и фактические scopes.
- Внешние Twitch API-запросы имеют ограничение времени ожидания; EventSub переподключается с увеличивающейся задержкой.
- Ответы в Twitch-чат отправляются последовательно с ограничением частоты.
